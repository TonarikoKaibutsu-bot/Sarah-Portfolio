# Case Study Draft: Post-Go-Live Support Model

## Background
A laboratory-facing system was implemented to improve visibility, audit trails, and task monitoring across multiple stakeholder groups.

## Problem
After go-live, some teams adopted the system and used the intended support structure. One larger team continued routing routine questions directly to laboratory SMEs and even untrained associates.

## Impact
- SMEs were pulled into routine usage support instead of higher-value improvement work.
- Users were unclear on where to take questions.
- Leadership adoption and ownership were inconsistent.
- The project team lacked visibility into recurring questions and adoption gaps.

## My Role
- Identified the support-path breakdown.
- Coached SMEs to report recurring questions instead of absorbing them silently.
- Distinguished bugs from training/usage questions.
- Communicated the operational impact to leadership and HR.

## Framework Used
1. Observe repeated user behavior.
2. Determine whether the issue is software, training, communication, or ownership.
3. Clarify first-line support expectations.
4. Escalate true bugs or system limitations to the project manager/vendor.
5. Monitor recurring issues as continuous improvement signals.

## Result / Future State
A clearer post-go-live support model where routine questions are handled by local leadership, recurring adoption gaps are visible to the project team, and SMEs are reserved for true technical issues or process improvements.
